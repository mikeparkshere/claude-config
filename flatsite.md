# Flat sites on RunCloud
You are helping build or maintain a small hand-coded site (typically under 10 pages) on a RunCloud-managed server. No WordPress, no CMS, no build step. PHP is used for includes and sitewide config only.

## Session startup (do this first, every time)

```bash
git -C ~/claude-config pull --ff-only
ls /home/runcloud/webapps/
```

Then say:

> "This server has the following webapps: [list them]. Which one are we working on today?"

Once confirmed:

```bash
cd /home/runcloud/webapps/[confirmed-app-name]/ && pwd
cat CLAUDE.md
```

The project CLAUDE.md should carry `stack: flatsite`. If there's no CLAUDE.md, say so and ask whether this is a new build or an inherited site before touching anything.

Then decide which mode you're in:

- **New build:** scaffold the structure below.
- **Inherited site:** follow "Converting an inherited site" below. Do not assume any standard organization until you've mapped what's there.

## The one rule

**Shared markup lives in `includes/` and nowhere else.** Never paste the header, footer, nav, `<head>` block, or a repeated CTA into a page file. If a page needs a variation, add a variable or a parameter to the include. Do not fork the markup.

Same for sitewide facts: business name, phone, address, hours, email, and social links live in `includes/config.php` only. Pages and partials read them from `$site`. NAP consistency across the site depends on this.

## Structure

```
[app-name]/                 <- webapp root, git repo root
  CLAUDE.md
  .gitignore
  includes/                 <- outside the docroot, never web-reachable
    bootstrap.php
    config.php
    config.local.php        <- secrets (Mailgun key), gitignored
    head.php
    header.php
    footer.php
    partials/               <- reusable sections (cta.php, testimonial.php, ...)
  tools/
    build-sitemap.php       <- CLI only
  public/                   <- RunCloud public path
    index.php
    about/index.php
    services/index.php
    contact/index.php
    404.php
    sitemap.xml             <- generated by tools/build-sitemap.php
    robots.txt
    assets/
      css/  js/  img/  fonts/
```

Set the webapp's **Public Path to `/public`** in RunCloud (Web Application → Settings). That keeps `includes/`, `tools/`, `CLAUDE.md`, and `.git` outside the docroot, so none of them can be requested over HTTP. If the inherited app's docroot is the webapp root and moving it isn't approved yet, add an nginx/htaccess deny for `/includes`, `/tools`, and `/.git` as a stopgap and note it in CLAUDE.md.

One directory per page (`about/index.php`) gives clean URLs with trailing slashes on any RunCloud stack with no rewrite rules.

## Scaffold

### `includes/bootstrap.php`
```php
<?php
define('INC', __DIR__);
require INC . '/config.php';
if (is_file(INC . '/config.local.php')) require INC . '/config.local.php';  // defines $secrets

function e($s) { return htmlspecialchars((string) $s, ENT_QUOTES, 'UTF-8'); }

function asset($path) {
    $file = $_SERVER['DOCUMENT_ROOT'] . $path;
    $v = is_file($file) ? filemtime($file) : '';
    return $path . ($v ? '?v=' . $v : '');
}

function partial($name, array $vars = []) {
    global $site, $page;
    extract($vars);
    include INC . '/partials/' . $name . '.php';
}

$page = array_merge([
    'title'       => $site['name'],
    'description' => '',
    'slug'        => '',
    'path'        => '/',
    'noindex'     => false,
    'body_class'  => '',
    'header'      => 'default',   // 'default' | 'transparent' (hero pages)
], $page ?? []);
```

### `includes/config.php`
```php
<?php
$site = [
    'name'    => '',
    'url'     => 'https://example.com',   // no trailing slash
    'phone'   => '',
    'email'   => '',
    'address' => ['street' => '', 'city' => '', 'state' => '', 'zip' => ''],
    'hours'   => [],
    'social'  => [],                       // ['facebook' => 'https://...']
    // Page registry: drives nav and the sitemap. Order = nav order.
    'pages'   => [
        'home'     => ['path' => '/',          'label' => 'Home',     'nav' => true],
        'about'    => ['path' => '/about/',    'label' => 'About',    'nav' => true],
        'services' => ['path' => '/services/', 'label' => 'Services', 'nav' => true],
        'contact'  => ['path' => '/contact/',  'label' => 'Contact',  'nav' => true],
    ],
];
```

### Page file (`public/about/index.php`)
```php
<?php
$page = [
    'title'       => 'About us | Business Name',
    'description' => 'One-sentence meta description.',
    'slug'        => 'about',
    'path'        => '/about/',
];
require $_SERVER['DOCUMENT_ROOT'] . '/../includes/bootstrap.php';
include INC . '/head.php';
include INC . '/header.php';
?>
<main id="main">
  <!-- page content -->
</main>
<?php include INC . '/footer.php'; ?>
```

Every page starts with that same require line, regardless of folder depth, because it's anchored to `DOCUMENT_ROOT`.

### `includes/head.php`
Owns `<!doctype>`, `<html lang="en">`, charset, viewport, `<title>`, meta description, canonical (`$site['url'] . $page['path']`), Open Graph tags, `noindex` when set, favicon links, and the stylesheet via `asset('/assets/css/main.css')` so CSS changes bust the cache without manual version numbers. Opens `<body>` with `$page['body_class']`.

### `includes/header.php`
Skip link to `#main`, logo, and nav built by looping `$site['pages']` where `nav` is true. The current page gets `aria-current="page"` when its key matches `$page['slug']`. Never hard-code nav links in markup.

Header variants come from `$page['header']`, which sets a modifier class on the `<header>` element (`site-header--transparent` for pages with a full-bleed hero, usually the homepage). One header partial, one class switch. Expect the rendered header to differ between page types because of this. That's by design, not drift.

### `includes/footer.php`
NAP from `$site`, social links, `© <?= date('Y') ?>`, LocalBusiness (or the right schema type) JSON-LD built from `$site` with `json_encode`, scripts via `asset()`, then closes `</body></html>`.

### `tools/build-sitemap.php`
CLI script that reads `$site['pages']` and writes `public/sitemap.xml`. Run it whenever a page is added, removed, or moved:

```bash
php tools/build-sitemap.php
```

### `public/404.php`
A normal page file with `'noindex' => true` that sends `http_response_code(404)`. Wire it up for the webapp's stack:
- Hybrid (nginx + Apache): `ErrorDocument 404 /404.php` in `public/.htaccess`
- Native nginx: add `error_page 404 /404.php;` through RunCloud's NGINX config for the webapp

### `.gitignore`
```
.DS_Store
*.log
/includes/config.local.php
/public/uploads-tmp/
```

One private GitHub repo per site, rooted at the webapp root. Secrets never go in the repo; `config.local.php` is created on the server by hand.

## Adding or changing a page

1. Create `public/[slug]/index.php` from the page template.
2. Add it to `$site['pages']` (set `nav` as needed).
3. Run `php tools/build-sitemap.php`.
4. Commit.

A sitewide change (nav item, phone number, footer link, new `<head>` tag) is one edit in `includes/`. If you find yourself editing more than one page file for a sitewide change, stop: the markup has leaked out of the includes.

## Conventions

- External CSS and JS only. No inline styles, no inline `<script>` except JSON-LD.
- Assets in `public/assets/css`, `/js`, `/img`, `/fonts`. Reference them as `/assets/...`.
- Escape every config value printed into HTML with `e()`.
- PHP stays at the include/config level: no database, no Composer, no npm, no frameworks. If a project needs more than that, it's not a flat site anymore. Raise it with Michael.
- Contact forms send through the Mailgun HTTP API by default (see Security). Check CLAUDE.md in case a site uses something else.
- Subdirectories with their own purpose (e.g. `/clients/*`, `/tools/*` under `public/`): ask whether they follow site-wide conventions or their own (inline styles allowed, looser CSP, etc.) before enforcing the rules above on them.

## Security

The attack surface is the contact form, the server, and anything that echoes request input. Hold these as rules:

- **Never include a path built from request input.** No `include $_GET[...]`, no routing by query string. Includes are fixed paths under `INC` only.
- **Escape all request input** printed into HTML with `e()`, including prefill values like `?service=`. Never print raw `$_GET`, `$_POST`, or `$_SERVER['REQUEST_URI']`.
- **Contact forms:** send with the Mailgun HTTP API (curl POST to the messages endpoint), never bare `mail()`. The API key comes from `$secrets` in `config.local.php`. Submitted fields go in the message body only; the one exception is `h:Reply-To`, which gets the visitor's address only after `filter_var($email, FILTER_VALIDATE_EMAIL)` passes. Strip CR/LF from anything used in the subject. Add a honeypot field (Turnstile if spam gets past it), and don't echo submitted values back without `e()`.
- **Own system user for new flat-site webapps** in RunCloud, even on a server shared with WordPress. Pick it at webapp creation; changing it later means recreating the webapp. Where an existing site shares a system user with WordPress, note it in CLAUDE.md.
- **Tamper check:** the server copy should always match the repo. A daily cron running `git -C [webapp root] status --porcelain` that alerts on any output catches files changed outside a deploy (for example by a compromised WordPress site under the same user).
- **Nothing but site files in `public/`.** No `.bak`, `.old`, `~`, `.swp`, `phpinfo.php`, or test scripts. Check with `find public -name '*.bak' -o -name '*~' -o -name '*.swp' -o -name 'phpinfo*'` before calling a session done.
- **`display_errors` off** in production. Log errors instead.
- **Security headers** (set in the RunCloud NGINX config or `.htaccess` on hybrid): HSTS, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, and a CSP that allowlists only the third-party hosts the site actually loads (analytics, fonts, embeds). Use `frame-ancestors 'self'` in the CSP.
- **Short-circuit WordPress bot traffic** with a bare nginx 404 for `/wp-*` and `/xmlrpc.php`, so it never reaches PHP or renders the branded 404.
- Run the newest PHP version RunCloud offers. Nothing here pins an older one.

## Environments and launch

Default flow: build on a staging webapp, launch to a fresh live webapp, then retire staging. No LocalWP step.

### Staging
- A subdomain on Michael's domain, on the same server the site will live on, so PHP version, nginx stack, and headers match production.
- Private, not just unindexed. Every SSL cert is publicly logged, so the subdomain is discoverable. Add basic auth (`auth_basic`) and an `X-Robots-Tag: noindex` header in this webapp's nginx config. Both live at the server level, never in the repo, so neither can ship to live. Don't use a `robots.txt` disallow.

### Environment settings
`config.php` holds production values. `config.local.php` (gitignored, written on the server by hand) overrides per environment:

```php
<?php
$env = 'staging';                              // 'staging' | 'production'
$site['url'] = 'https://[sub].example.com';    // drives canonicals, OG, sitemap
$secrets = [
    'mailgun_key'    => '',
    'mailgun_domain' => '',
    'form_to'        => '',                     // Michael on staging, client on production
];
```

### Launch
1. Create the live webapp (own system user where possible, public path `/public`).
2. Clone the repo into it.
3. Write `config.local.php` with `$env = 'production'`, the apex URL, and the client's form recipient.
4. Run `php tools/build-sitemap.php`.
5. Add the apex (and `www`) domains and issue SSL.
6. Point DNS.
7. Add 301s from the old site's URLs.
8. Submit a test form and confirm it arrives.
9. Michael deletes the staging webapp in RunCloud. Keep the subdomain's DNS record for reuse.

### After launch
Small edits (copy, hours, prices, a new page) are made on live and committed to GitHub before the session ends, so the tamper check stays clean. If a change goes wrong, `git revert` puts it back.

Recreate staging only when:
- The client needs to review or approve something before it goes live (new section, promo, redesign).
- The change can break the site in ways only visible on the server: security headers or CSP, nginx rules, the contact form or Mailgun setup.
- The work spans several sessions and live has to stay untouched in the meantime.

To recreate: new webapp on the subdomain, clone the repo, write a staging `config.local.php`, add auth and the noindex header. When the work merges and deploys, delete it again.

## Converting an inherited site

1. **Map what exists.** List every file and folder, the docroot, and the RunCloud stack type.
2. **Diff the repeated blocks.** Compare `<head>`, header, nav, and footer across every page. Note each variation (different titles and descriptions are expected; a stray link on one page usually isn't). Report the variations to Michael before you normalize them.
3. **Identify what's redundant or broken.** Unused assets, duplicate CSS, dead links, missing meta.
4. **Propose the new structure** using the layout above, with a list of what moves where and any URL changes. If URLs change, include the 301 redirect list.
5. **Convert after approval.** Build `includes/` from the normalized markup, convert each page to the page template, set the public path, generate the sitemap, and add redirects.

Before proposing URL changes, ask Michael whether the site has search traffic or backlinks worth checking in Search Console. The file list shows the old URLs, not which ones matter.

### Partially conforming sites

If the site already uses PHP includes with a different layout (other folder names, a different bootstrap, includes inside the docroot), don't restructure it to match this doc for its own sake. Align what affects safety and maintenance, and leave a working structure alone:

- **Always fix:** secrets inside the docroot or in git, includes or routing driven by request input, unescaped request input, includes reachable over HTTP (move them out, or deny the path as a stopgap), stray backup files in the docroot, and anything else in the Security section.
- **Fix if missing:** sitemap, canonical tags, a custom 404 with a real 404 status, cache-busted assets, and sitewide facts kept in one place.
- **Leave as is unless Michael asks:** folder names, file naming, how the bootstrap is wired, and CSS organization.

Record the site's actual layout in its CLAUDE.md so future sessions follow that site's conventions instead of this doc's defaults.

## When to step up to a generator

Move to Eleventy (not this stack) when the site needs content generated from data: a blog, team bios, service or location pages built from a list, or a directory. Also consider it when the site will deploy to static hosting (Cloudflare Pages, Netlify) where PHP isn't available. Flag it to Michael rather than bolting collections onto this setup.
